# 前後端功能落差整理清單 (給後端)

本文件整理了 **Dietary App** 目前「前端已實作介面與交互邏輯，但後端尚未提供 API 支援」的功能缺口，供後端開發參考。

## 1. 登入與認證 (Login / Auth)
  **Token 安全性優化**：
    *   **前端現況**：已實作基礎 JWT 存儲。
    *   **後端缺口**：尚未實作 **Refresh Token** 機制，導致 Token 過期後使用者必須重新登入。* 

## 2. 個人首頁 (Profile Page)
*   **帳號註銷實體邏輯 (Account Deletion)**：
    *   **前端現況**：已實作「刪除帳戶」按鈕與二次確認流程。
    *   **後端缺口**：雖有 API 定義，但缺失實質的物理刪除邏輯（需刪除 User 及其關聯的 Profile 與紀錄）。
*   **頭像持久化 (Profile Image)**：
    *   **前端現況**：已實作相簿選取並顯示。
    *   **後端缺口**：資料庫 `UserProfile` 需補上 `image_url` 欄位，並提供處理檔案上傳的 API。
*   **API 回傳欄位一致性 (Admin Role)**：
    *   **現況分析**：後端已有 `ROLE_ADMIN` 邏輯，但 `/api/user/profile` 預設回傳的 JSON 結構中，`User` 物件被嵌套在內，前端建議後端可考慮將 `role` 欄位扁平化回傳，以提升解析效率。

## 3. 飲食紀錄與報告 (Dietary Records)
*   **手動紀錄存檔接口 (Manual Record API)**：
    *   **前端現況**：已實作 `ManualRecordPage`（包含時段自動判定與動態項目清單）。
    *   **後端缺口**：目前僅有管理員級別的紀錄 API，需為一般使用者補上 `POST /api/user/diet-records` 接口，用以儲存文字輸入的飲食內容。
*   **紀錄時間軸讀取 (Timeline Fetching)**：
    *   **前端現況**：飲食紀錄頁面具備「S 型時間軸」UI。
    *   **後端缺口**：需提供 API 讓前端讀取該使用者的歷史進食日期，以便在時間軸的圓點上顯示「已記錄」或「未記錄」狀態。
*   **趨勢統計與 Aggregation**：
    *   **前端現況**：報表頁面具備日/週切換圖表。
    *   **後端缺口**：需補強資料庫統計邏輯，能根據日期區間自動計算熱量與營養素總和，而非僅回傳原始清單。

## 4. 預設首頁與小精靈 (Home / Chat)
*   **對話紀錄持久化 (Chat Persistence)**：
    *   **前端現況**：具備對話介面，但跳頁後紀錄會消失。
    *   **後端缺口**：缺失儲存使用者與小精靈對話內容的資料庫。
*   **動態建議引擎 (Recommendation API)**：
    *   **前端現況**：已實作關鍵字觸發（如「早午餐」）與選項按鈕。
    *   **後端缺口**：需實作 API 根據使用者目標動態產出食物建議清單，而非使用前端 Mock Data。

## 5. 需要討論的功能 (To be discussed)
### 管理員初次登入個資填寫
*   **現況描述**：系統預設 `admin` 帳號因缺乏對應的 `UserProfile` 資料，導致登入後仍導向引導頁面。
*   **建議選項**：1. 維持現狀，讓管理員手動填寫一次以建立完整檔案。2. 修改後端初始化邏輯，自動為 admin 塞入預設虛擬數據以跳過引導。
