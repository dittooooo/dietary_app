## 1. 問卷頁把狀態、輸入驗證、API 與大量 Painter 放在同一檔案

- **檔案與行號**：`views/auth/initial_info_page.dart:18-1203`、`1213-1913`
- **原始碼片段**：`class InitialInfoPage ...` 同時包含 `_completeSetup()`、多個 `_buildPage...()`，以及 `HandDrawnNotebookPainter`、`HandDrawnBoxPainter` 等多個繪圖類別。
- **原因**：單檔約 1,900 行，問卷流程、資料轉換、儲存、畫面元件與繪圖互相牽連，修改一個欄位容易影響翻頁或 Painter。這是責任過度集中，不代表目前一定有執行錯誤。
- **優先度**：優先度中
- **難易度**：難易度困難
- **目前證據**：同一個 State 類別與同一檔案尾端同時存在流程方法與多個 CustomPainter；本輪不將已不在現行程式碼中的舊 helper 當成證據。
- **驗證方式**：先畫出問卷資料模型、頁面元件、提交流程與 Painter 的依賴，再逐段抽離；測試每頁翻頁、返回、驗證、提交成功與失敗。
- **完成條件**：問卷 State 不再直接承擔所有繪圖與資料轉換；拆分後行為、API payload 與返回登入／首頁流程一致。

## 2. 成功過渡頁的流程責任需要維持清楚

- **檔案與行號**：`views/auth/success_transition_page.dart:91-244`
- **原始碼片段**：`_runTransition()` 依序呼叫 `_checkOnboarding()`、`_settleDailyScores()`、`_playBodyTypeChangeIfNeeded()` 與 `_animateProgress()`。
- **原因**：登入後的導頁、問卷狀態確認、每日結算、體態動畫與本地狀態保存集中在一個流程。未來若重複呼叫或改變順序，容易造成使用者看到錯誤頁面或結算兩次。
- **優先度**：優先度中
- **難易度**：難易度中
- **目前證據**：目前已使用 `AuthService` 與 `BodyStatusApiService`，沒有重新發現先前所述的裸 `http.get`；舊分析若指稱仍有裸 HTTP，標記為需重新驗證。
- **驗證方式**：測試新登入、已完成問卷、未完成問卷、結算失敗、網路中斷與重複進入頁面。
- **完成條件**：成功頁只負責流程編排；API、session 與動畫狀態的成功／失敗契約清楚且可測試。

## 3. 個人頁的資料載入與頭像更新要維持單一來源

- **檔案與行號**：`views/auth/profile_page.dart:45-159`
- **原始碼片段**：`_loadUserData()` 先讀本地暱稱／角色，再呼叫 `AuthService().getUserProfile()`；`_pickImage()` 上傳成功後再次呼叫 `_loadUserData()`。
- **原因**：本地快取、後端 profile、角色判斷與頭像畫面更新集中在頁面內。若其他頁面沒有同步同一份頭像狀態，會出現上傳成功但右上角仍顯示舊圖的問題。
- **優先度**：優先度中
- **難易度**：難易度中
- **目前證據**：頁面同時依賴 SharedPreferences 與後端回傳；目前已存在共用頭像狀態控制器，後續應確認所有頭像入口都使用它。
- **驗證方式**：不同帳號各自上傳頭像，切換首頁、飲食紀錄、報告與個人頁，再登出登入確認不串圖。
- **完成條件**：頭像 URL 的解析、快取失效與跨頁同步只有一套規則；不再由各頁自行拼接或保存互相衝突的 URL。
