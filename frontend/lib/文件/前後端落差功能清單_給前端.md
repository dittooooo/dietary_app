# 前後端功能落差整理清單 (給前端)

本文件詳列了目前 **後端已實作** 完整 API 邏輯，但 **前端尚未完全對接**、僅有初步佔位或使用模擬數據（Mock Data）的功能清單。請前端開發團隊根據此清單逐步進行 API 連接。

---

## 1. 登入與權限管理 (Auth & Role Management)
*   **後端已實作**：
    *   後端已實作強大的 JWT 權限管理系統，並在資料庫中區分了 `ROLE_USER` 與 `ROLE_ADMIN`。
    *   實作了嚴格的權限守衛，非 `ROLE_ADMIN` 帳號若嘗試調用 `/api/admin/**` 接口皆會回傳 `403 Forbidden`。
*   **前端需補強**：
    *   目前前端對「管理員」的身分判讀邏輯分散在各頁面（如 `ProfilePage` 的手動檢查）。應在 `AuthService` 中統一處理身分判別。
    *   前端需要補上 **「全域權限降級/攔截處理」**：當一般使用者強行點入管理頁面，或是後端 API 回傳 `403` 時，應有友善的導航攔截並將使用者導向一般用戶首頁。

## 2. 個人首頁與頭像持久化 (Profile & Avatar)
*   **後端已實作**：
    *   `UserProfileController` 提供 `/api/user/profile` 獲取與更新個人資料。
    *   `AvatarController` 已實作 `POST /api/user/avatar`，供一般用戶上傳自己的大頭照，上傳成功後會將圖片路徑寫入該用戶的 `UserProfile` 並返回 URL。
*   **前端需補強**：
    *   目前 `ProfilePage` 中的頭像選擇功能 `_pickImage()` 僅將圖片讀取為記憶體數據（`_imageBytes`）並在本地展示，**完全沒有調用後端頭像上傳 API**。這導致用戶重新開啟 App 後，頭像會回到預設值。
    *   應儘速對接 `POST /api/user/avatar` 接口，在圖片選取完成後進行異步上傳，並在 `_loadUserData()` 時正確讀取後端回傳的頭像路徑。

## 3. 一般使用者飲食紀錄與報告 (User Dietary Records)
*   **後端已實作**：
    *   `UserProfileController` 與 `DietRecordController` 下已實作完整的個人紀錄 API：
        *   `GET /api/diet-records` / `GET /api/user/diet-records`：獲取當前登入用戶的所有歷史飲食紀錄。
        *   `POST /api/diet-records` / `POST /api/user/diet-records`：手動上傳個人的進食紀錄（包含食物、熱量、蛋白質、脂肪、碳水化合物等）。
        *   `PUT /api/diet-records/{id}`：修改特定的飲食紀錄。
        *   `DELETE /api/diet-records/{id}`：刪除特定的飲食紀錄。
        *   `POST /api/diet-records/{id}/photo`：為該筆紀錄上傳餐點照片。
*   **前端需補強**：
    *   前端目前的 `diary_page.dart`（飲食日記）、`dietary_record_page.dart`（飲食紀錄頁面）、`manual_record_page.dart`（手動紀錄頁面）、`report_page.dart`（報表頁面）**完全沒有進行 API 呼叫，所有的紀錄與圖表皆使用 Mock Data**。
    *   應串接並補強以下邏輯：
        1. 在 `manual_record_page.dart` 填寫完成後，調用 `POST /api/diet-records`。
        2. 如有拍照，在新增成功拿到 ID 後，調用 `POST /api/diet-records/{id}/photo` 上傳照片。
        3. `diary_page.dart` 中的 S 型時間軸與歷史進食列表，應改為向後端發送 `GET /api/diet-records` 獲取真實紀錄。
        4. `report_page.dart` 的日/週趨勢統計圖表，應請求真實資料進行前端加總計算與動態繪製，而非顯示寫死的測試圖形。

## 4. 管理者面板 - 使用者管理 (Admin User Management)
*   **後端已實作**：
    *   `AdminController` 下具備完整的使用者 CRUD 與頭像控制 API：
        *   `GET /api/admin/users` (支援關鍵字 `keyword` 搜尋與列出全系統使用者)
        *   `GET /api/admin/users/{id}` (獲取指定使用者詳情與個資)
        *   `POST /api/admin/users` (管理員確認新增使用者)
        *   `PUT /api/admin/users/{id}` (管理員編輯指定使用者資訊)
        *   `DELETE /api/admin/users/{id}` (管理員物理刪除使用者)
        *   `POST /api/admin/users/{userId}/avatar` (管理員為指定使用者上傳頭像)
*   **前端需補強**：
    *   目前的 `AdminUserListPage` 使用的是硬編碼的模擬資料（如王小明、李華等），且刪除按鈕僅進行本地陣列的 `removeWhere`，**完全沒有任何後端 API 對接**。
    *   應將搜尋框、新增（`FloatingActionButton`）、詳情頁跳轉（`UserDetailPage`）以及刪除確認彈窗，全面對接至 `/api/admin/users/**` 相應的 API 接口，實現真實的管理員使用者維護功能。

## 5. 管理者面板 - 餐廳與菜單管理 (Admin Restaurant & Menu Management)
*   **後端已實作**：
    *   `AdminController` 下已實作餐廳與菜單的完整 API：
        *   餐廳管理：`GET`/`POST`/`PUT`/`DELETE` `/api/admin/restaurants/**` (支援依名稱查詢與 CRUD)。
        *   菜單管理：`GET`/`POST`/`PUT`/`DELETE` `/api/admin/menus/**` (支援依餐點名稱查詢與 CRUD)。
*   **前端需補強**：
    *   目前小精靈對話框中的「餐廳推薦」均為寫死的 Mock Data。應改為 **「動態資料串接」**：當使用者諮詢建議時，小精靈應調用後端已建立的真實餐廳與菜單清單進行推薦。
    *   前端「管理員選單」中的「菜單管理」（`GenericAdminListPage`）點入後僅會延遲 600ms 並顯示空列表。應儘速開發餐廳與菜單維護介面，並對接後端 CRUD API。

## 6. 管理者面板 - 全系統飲食紀錄監控 (Admin Diet Records Monitoring)
*   **後端已實作**：
    *   `AdminController` 下提供了供管理員調用的全系統紀錄操作接口：
        *   `GET /api/admin/diet-records` (支援 `userId`, `nickname`, `dishName`, `date`, `mealType` 多條件篩選篩查)
        *   `POST /api/admin/diet-records` (幫特定用戶手動補登紀錄)
        *   `PUT /api/admin/diet-records/{id}` (修正異常數據)
        *   `DELETE /api/admin/diet-records/{id}` (刪除違規或錯誤的飲食數據)
*   **前端需補強**：
    *   目前前端「管理員選單」中的「飲食紀錄管理」同樣為 `GenericAdminListPage` 佔位頁。
    *   應設計並實作 **「全系統紀錄監控台」**，允許管理員透過篩選條件快速查詢全系統所有使用者的近期進食數據，並能進行線上修改或異常資料清除。

## 7. 飲食智能小精靈與週報告分析 (Weekly Analysis & Chat)
*   **後端已實作**：
    *   `DietaryAgentController` 已實作 `POST /api/dietary/ask-weekly-analysis`。
    *   該接口接收 `DietaryAskRequest` (僅包含 `question` 字串)，並在後端自動結合該登入使用者的 `UserProfile` 與過去 7 天的 `DietRecord` 進行整合。
    *   回傳格式為 `DietaryAgentPayload` 的 JSON 結構，具體包含：
        *   `question` (使用者提問)
        *   `user_profile` (個人基本身高、體重、性別、年齡、目標)
        *   `health_condition` (包含慢性病紀錄：`has_chronic_disease` 與 `chronic_diseases` 列表)
        *   `weekly_diet_records` (過去七天的飲食紀錄列表，包含日期 `date`、餐別 `meal`、餐點 `dish_name` 與備註 `note`)
*   **前端需補強**：
    *   目前的 `home_view.dart` 中，使用者與小精靈的對話（如「早午餐推薦」或諮詢對話）之回答皆是前端寫死的固定文字。
    *   應全面串接 `POST /api/dietary/ask-weekly-analysis`，當使用者在首頁向小精靈諮詢時，將提問傳送至後端，並解析回傳的整合性 JSON 資料以供前端做後續的 AI 呈現或建議生成。

## 💡 前端串接後功能測試指南 (如何測試)

當前端開發人員完成上述功能的程式碼編修與 API 串接後，請依循以下具體步驟進行手動驗證，確保功能與後端完美對接：

### 準備工作：啟動本地後端與確認連線
1. **啟動 Spring Boot 後端**：確保後端專案已成功啟動（預設連接埠為 `8080`）。
2. **確認 API 位址設定**：打開前端 `frontend/lib/config/api_config.dart`，確認 `baseUrl` 對應的 IP 與 Port 設定正確（若使用實體手機測試，需與電腦連至同一 Wi-Fi 並使用電腦的本地局域網 IP，例如 `192.168.x.x`；若使用模擬器，可使用 `10.0.2.2` 或 `localhost`）。

---

### 測試情境 1：登入與權限守衛測試
1. **註冊新帳號**：
   * 在註冊頁面輸入新 Email 並註冊，確認能順利進入 **Onboarding (引導填寫個資)** 頁面。
   * 填寫完身高、體重等資料送出，確認能成功跳轉至 App 首頁（此時後端 User 的 `hasCompletedOnboarding` 應被標記為 true）。
2. **一般使用者登入**：
   * 使用剛註冊的帳號登入，進入「個人首頁」，確認「管理員選單」**不會**顯示。
   * 手動嘗試在代碼中強制導向管理頁面（或觸發 `/api/admin` 請求），確認後端會回傳 `403 Forbidden`，且前端能攔截並跳出「權限不足」的提示，將你導回一般首頁。
3. **管理員登入**：
   * 使用管理員帳號（預設為 `admin@gmail.com`，密碼依後端設定）登入。
   * 確認「個人首頁」中成功出現「管理員選單」區塊。

---

### 測試情境 2：大頭貼上傳與持久化測試
1. **上傳頭像**：
   * 在「個人首頁」點擊頭像旁的相機按鈕，從相簿選擇一張圖片。
   * 選擇圖片後，確認 UI 立即更新顯示新頭像。
2. **持久化驗證**：
   * **重啟 App（完全關閉後重新開啟）** 並重新登入，或者直接在個人首頁「下拉刷洗」。
   * 確認頭像**依然顯示為剛剛上傳的圖片**，而非變回預設人像（這代表前端成功呼叫 `POST /api/user/avatar`，且重新載入時 `GET /api/user/profile` 回傳的 `avatarUrl` 有被正確載入）。

---

### 測試情境 3：飲食紀錄與報告測試
1. **手動新增飲食紀錄**：
   * 前往手動紀錄頁面，新增一筆餐點（例如：午餐、雞肉沙拉、熱量 400 kcal）。
   * 點擊確認後，至「飲食日記（S 型時間軸）」頁面，確認時間軸上對應的時間點出現了剛才新增的「雞肉沙拉」。
   * **拍照上傳測試**：在新增紀錄時選取相片，確認後端上傳無報錯，且日記中該紀錄能讀取到圖片。
2. **紀錄編輯與刪除**：
   * 在日記中點擊該筆紀錄進入編輯，修改熱量或餐點名稱，儲存後確認日記列表同步更新。
   * 點擊刪除按鈕，確認該筆紀錄從 S 型時間軸消失。
3. **報表趨勢圖**：
   * 連續新增 3~4 筆不同日期的飲食紀錄。
   * 切換至「報表頁面」，確認長條圖/折線圖的數值有隨著你新增的熱量動態起伏，而非固定的靜態 Mock 圖案。

---

### 測試情境 4：管理者面板功能測試
1. **使用者管理清單**：
   * 登入 Admin 帳號，點進「使用者管理」。
   * 確認清單列出的是資料庫中的真實註冊使用者，而非之前的模擬資料。
   * 在搜尋框輸入關鍵字（例如步驟一註冊的 Email），確認能精準篩選出來。
   * 點入使用者詳情，確認顯示的身高、體重與你的資料庫相符。
   * 點擊刪除按鈕，確認使用者被強制登銷，且該使用者使用原帳密再也無法登入。
2. **菜單與餐廳管理**：
   * 點進「菜單管理」，確認列表可以讀取現有菜單。
   * 點擊新增按鈕，新增一家餐廳（如：「健康廚房」）與菜色（如：「藜麥雞胸肉飯」）。
   * 到一般使用者的對話小精靈諮詢「推薦餐廳」，確認小精靈能動態把剛才新增的「健康廚房」呈現在卡片中。
3. **全系統飲食紀錄監控**：
   * 點進「飲食紀錄管理」，確認畫面上列出全系統所有使用者的近期進食明細。
   * 使用篩選器篩選特定使用者，並嘗試進行修改或刪除，確認該使用者的個人日記同步被變更。

---

### 測試情境 5：智能小精靈對話與週報告測試
1. **對話功能測試**：
   * 在首頁的對話框隨意輸入一句問題，點擊送出。
   * 確認前端有向後端 `POST /api/dietary/ask-weekly-analysis` 發送請求。
   * 查看終端機（Terminal）或網路攔截日誌，確認送出的 payload 中，自動帶上了你的個人檔案資料（體重、身高、慢性病）以及過去七天的飲食紀錄，並確認對話框有顯示回傳的 AI 分析建議。
