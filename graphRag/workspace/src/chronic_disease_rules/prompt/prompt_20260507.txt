你現在要協助我整理「慢性疾病飲食規則資料」，目標是產出可直接用於 Knowledge Graph 與 Recommendation System 的 JSON 檔案。

請你依照 workspace/src/chronic_disease_rules 資料夾中現有的程式碼、資料格式與附檔內容進行修改與產出，不要重新設計完全不同的架構，請盡量沿用現有欄位命名、資料結構與處理流程。
資料來園一律參考: workspace/src/chronic_disease_rules/data 內的檔案
一、任務目標

我要建立一份慢性疾病飲食規則 JSON。
這份資料未來會用在知識圖譜中，主要處理「疾病節點」與「營養成分節點」之間的關係。
知識圖譜的核心不是：
Disease → Food

而是：
Disease → Nutrition Component
食物只能作為 example_foods 或輔助說明，不應該成為疾病直接連結的主要對象。

也就是說，原始參考資料可能會寫：
高血壓應少吃鹹食、泡麵、醃漬品

但你要整理成：
高血壓 limit 鈉 Sodium

而不是：
高血壓 limit 泡麵

原因是泡麵被限制，是因為它通常含有高鈉。

二、營養成分主檔規則

本次整理疾病資料時，所有和營養成分相關的定義都必須以 nutrition_components.json 為主檔來源。
nutrition_components.json 是營養成分類別資料，裡面包含所有可被 Knowledge Graph 使用的營養成分節點。

每一筆營養成分主檔格式如下：
{
  "nutrition_id": "NUT017",
  "name_zh": "鈉",
  "name_en": "Sodium",
  "unit": "mg",
  "category": "mineral",
  "source_column": "鈉(mg)"
}

疾病規則中的所有營養成分欄位，必須優先從 nutrition_components.json 取得。

也就是說，disease_nutrition_relations 裡面的營養成分必須使用：

1. nutrition_id
必須使用 nutrition_components.json 內既有的 nutrition_id，或是依照本 prompt 第三段規則新增的 NNUT 編號。
例如：
鈉必須使用 NUT017
飽和脂肪必須使用 NUT006
膳食纖維必須使用 NUT009
反式脂肪必須使用 NUT083
膽固醇必須使用 NUT103
酒精含量必須使用 NUT104

2. nutrition_name_zh
必須使用 nutrition_components.json 內的 name_zh，或是新增 NNUT 時定義的 name_zh。

3. nutrition_name_en
必須使用 nutrition_components.json 內的 name_en，或是新增 NNUT 時定義的 name_en。

4. nutrition_unit
必須使用 nutrition_components.json 內的 unit，或是新增 NNUT 時定義的 unit。

5. nutrition_category
必須使用 nutrition_components.json 內的 category，或是新增 NNUT 時定義的 category。

6. source_column
必須使用 nutrition_components.json 內的 source_column，或是新增 NNUT 時定義的 source_column。

禁止使用 snake_case 自行命名作為 nutrition_id。
禁止在 disease_nutrition_relations 中使用沒有被定義在 nutrition_components.json 的營養成分。
若需要新增營養成分，必須先依照第三段規則新增至 nutrition_components.json，再於 disease_nutrition_relations 使用。

例如：

如果想表達「高血壓限制鈉」，必須寫：

{
  "relation": "limit",
  "nutrition_id": "NUT017",
  "nutrition_name_zh": "鈉",
  "nutrition_name_en": "Sodium",
  "nutrition_unit": "mg",
  "nutrition_category": "mineral",
  "source_column": "鈉(mg)"
}

不可以寫：

{
  "relation": "limit",
  "nutrient_id": "sodium",
  "nutrient_name_zh": "鈉",
  "nutrient_name_en": "Sodium"
}

因為本專案的營養成分節點 ID 不是 sodium，而是 nutrition_components.json 中定義的 NUT017。

三、營養成分映射規則

請將疾病飲食建議轉換成 nutrition_components.json 中已存在的營養成分。
但如果某個疾病規則確實需要使用的營養成分不存在於 nutrition_components.json，請依照以下規則處理：

1. 優先尋找可合理替代的既有營養成分

如果原始概念不存在於 nutrition_components.json，但可以在不影響飲食建議原則與推薦邏輯的前提下，簡化或映射到既有營養成分，請優先使用既有營養成分，不要新增。

例如：

可溶性膳食纖維不存在於 nutrition_components.json，但膳食纖維已存在。
因此可溶性膳食纖維應簡化為：

nutrition_id: NUT009
name_zh: 膳食纖維
name_en: Dietary Fiber

並在 target_rule.note 或 reason 中說明：

「原始資料提到可溶性膳食纖維，但 nutrition_components.json 目前只有膳食纖維總量，未區分可溶性與不可溶性纖維，因此以膳食纖維作為系統可計算欄位。」

其他類似例子：

- 精製碳水化合物不存在，但可暫時映射到 NUT008 總碳水化合物，並在 note 說明這是碳水來源品質問題
- 添加糖不存在，但可視情境映射到 NUT010 糖質總量，並在 note 說明資料庫目前以糖質總量作為可計算欄位
- Omega-3 脂肪酸總量不存在，但可拆成資料庫中已有的 NUT075 次亞麻油酸(18:3)、NUT078 廿碳五烯酸(20:5)、NUT080 廿二碳六烯酸(22:6)

2. 若沒有合理替代項，才新增營養成分

如果某個營養成分或飲食因子在疾病飲食規則中非常重要，而且 nutrition_components.json 中完全沒有相似或可替代的營養成分，請自行新增到 nutrition_components.json。

新增時必須依照 nutrition_components.json 既有格式建立資料：

{
  "nutrition_id": "NNUT001",
  "name_zh": "...",
  "name_en": "...",
  "unit": "...",
  "category": "...",
  "source_column": null
}

新增營養成分 ID 規則：

1. 新增的 nutrition_id 必須以 NNUT 開頭，代表 new nutrition
2. 編號從 NNUT001 開始
3. 後續新增依序為 NNUT002、NNUT003、NNUT004
4. 不可和既有 NUT001–NUT104 混用
5. 不可重複使用已新增過的 NNUT 編號

新增營養成分時的欄位規則：

1. nutrition_id
使用 NNUT001 開始的新編號。

2. name_zh
使用繁體中文正式名稱。

3. name_en
使用英文正式名稱。

4. unit
若該成分可量化，請填入合理單位，例如：
mg
g
ug
kcal

若目前資料來源無法量化，請填 null。

5. category
請依照 nutrition_components.json 既有分類邏輯填寫。
可使用既有 category，例如：
energy
general_nutrition
mineral
vitamin
fatty_acid
sugar
amino_acid

若該概念不屬於既有分類，但仍需作為推薦系統規則使用，可使用：
dietary_factor

6. source_column
因為新增成分通常不是原始營養資料庫欄位，請填 null。
若未來有對應欄位，再補上欄位名稱。

3. 新增後的營養成分可以建立 Disease-Nutrition 關係

如果某個營養成分已經新增到 nutrition_components.json，就可以在 disease_nutrition_relations 中使用它。

例如：

若 Purine 普林不在 nutrition_components.json，且痛風與高尿酸血症規則中確實需要使用 Purine，且沒有合理替代的既有營養成分，請新增：

{
  "nutrition_id": "NNUT001",
  "name_zh": "普林",
  "name_en": "Purine",
  "unit": "mg",
  "category": "dietary_factor",
  "source_column": null
}

之後疾病規則中可以使用：

{
  "relation": "limit",
  "nutrition_id": "NNUT001",
  "nutrition_name_zh": "普林",
  "nutrition_name_en": "Purine",
  "nutrition_unit": "mg",
  "nutrition_category": "dietary_factor",
  "source_column": null
}

4. 不要把非營養概念硬加成營養成分

不是所有飲食建議都應該新增到 nutrition_components.json。

只有「可以被視為營養成分、食物成分、飲食因子，且會直接影響疾病飲食建議」的概念才可以新增。

可以考慮新增的例子：

- 普林 Purine
- 咖啡因 Caffeine
- 辛辣刺激成分 Spicy Compounds
- 酸性成分 Acidic Components
- 碳酸 Carbonation

不建議新增的例子：

- 內臟
- 海鮮
- 泡麵
- 醃漬品
- 油炸食品
- 甜點
- 手搖飲
- 宵夜
- 大餐

這些是食物、料理或飲食情境，不是營養成分。
它們應該放在 example_foods 或 non_nutrition_rules，不應該新增成 nutrition component。

5. 新增與簡化的判斷優先順序

請依照以下順序判斷：

第一步：nutrition_components.json 是否已有完全相同營養成分？
如果有，直接使用既有 nutrition_id。

第二步：nutrition_components.json 是否有不影響飲食原則的相似營養成分？
如果有，使用既有營養成分，並在 note 說明簡化原因。

第三步：該概念是否是疾病飲食規則中重要且可被視為營養成分或飲食因子？
如果是，新增到 nutrition_components.json，使用 NNUT001 起編。

第四步：如果該概念只是食物、料理、飲食情境或難以量化的行為描述，請不要新增到 nutrition_components.json，改放在 example_foods、non_nutrition_rules 或 unmapped_concepts。

五、核心知識圖譜規則

每一種疾病都要整理成 disease node 與 nutrition component node 的關係。

疾病與營養成分之間只允許以下三種 relation：

1. recommend
代表此疾病建議增加、優先選擇、適量攝取的營養成分。

例如：
高血脂 recommend 膳食纖維
高血脂 recommend 脂肪酸M總量
糖尿病 recommend 膳食纖維

2. limit
代表此疾病需要限制、減少、控制攝取量的營養成分。

例如：
高血壓 limit 鈉
高血脂 limit 飽和脂肪
糖尿病 limit 糖質總量
慢性腎臟病 limit 鈉、磷、鉀、粗蛋白

3. prohibit
代表此疾病應避免或盡量不要攝取的營養成分。

注意：
prohibit 不代表醫學上絕對禁止，而是對推薦系統而言屬於高風險、應強烈避免的項目。

例如：
高血脂 prohibit 反式脂肪
心血管疾病 prohibit 反式脂肪
痛風 prohibit 酒精含量

六、資料整理原則

請將原始參考資料中的「推薦食物」、「限制食物」、「禁止食物」轉換成背後對應的營養成分原因。

轉換範例：

1. 若參考資料說「高血壓少吃泡麵、醃漬品、加工食品」
應轉換成：
疾病：Hypertension
relation：limit
nutrition_id：NUT017
nutrition_name_zh：鈉
nutrition_name_en：Sodium
reason：高鈉攝取會提高血壓並增加心血管風險
example_foods：泡麵、醃漬品、加工食品

2. 若參考資料說「高血脂少吃肥肉、奶油、香腸」
應轉換成：
疾病：Hyperlipidemia
relation：limit
nutrition_id：NUT006
nutrition_name_zh：飽和脂肪
nutrition_name_en：Saturated Fat
reason：飽和脂肪會提高 LDL-C
example_foods：肥肉、奶油、香腸

3. 若參考資料說「糖尿病避免含糖飲料、甜點」
應轉換成：
疾病：Diabetes Mellitus
relation：limit 或 prohibit
nutrition_id：NUT010
nutrition_name_zh：糖質總量
nutrition_name_en：Total Sugars
reason：糖質攝取過多會使血糖控制困難
example_foods：含糖飲料、甜點

4. 若參考資料說「痛風避免啤酒」
應轉換成：
疾病：Gout
relation：prohibit
nutrition_id：NUT104
nutrition_name_zh：酒精含量
nutrition_name_en：Alcohol
reason：酒精會影響尿酸代謝並增加痛風發作風險
example_foods：啤酒、烈酒

5. 若參考資料說「痛風避免內臟、部分海鮮」
應先判斷背後原因是否可映射到 nutrition_components.json。
若原因是 Purine，且 nutrition_components.json 中沒有 Purine，也沒有合理替代的既有營養成分，請依照第三段規則新增 NNUT001 普林，再建立 disease_nutrition_relations。
內臟、海鮮本身不可成為營養成分節點，應放在 example_foods。

七、每個疾病 JSON 格式

每一個疾病都應整理成以下格式。

{
  "disease_id": "hyperlipidemia",
  "disease_name_zh": "高血脂",
  "disease_name_en": "Hyperlipidemia",
  "disease_nutrition_relations": [
    {
      "relation": "recommend",
      "nutrition_id": "NUT009",
      "nutrition_name_zh": "膳食纖維",
      "target_rule": {
        "daily_target": "25–30 g/day",
        "unit": "g/day",
        "direction": "increase",
        "note": "資料庫目前只有膳食纖維總量，未區分可溶性與不可溶性纖維"
      },
      "food_level_rule": {
        "basis": "per_100g",

八、每個 disease_nutrition_relation 的欄位要求

每一筆 disease_nutrition_relation 至少包含：

1. relation
只能是 recommend、limit、prohibit 三者之一。

2. nutrition_id
必須來自 nutrition_components.json。
可以是原本存在的 NUT 編號，也可以是依照第三段規則新增到 nutrition_components.json 的 NNUT 編號。
不可使用 snake_case 自訂 ID。
不可使用 sodium、saturated_fat、dietary_fiber 這種自行命名作為主 ID。

3. nutrition_name_zh
必須來自 nutrition_components.json 的 name_zh。

4. target_rule
描述每日目標、限制、方向、單位、注意事項。
常見欄位可以包含：
daily_target
daily_limit
weekly_target
max
optimal
unit
direction
note

direction 只能使用以下語意：
increase：建議增加
decrease：建議減少
avoid：建議避免
replace：建議取代
maintain：建議維持
adjust_by_stage：依疾病階段調整

5. food_level_rule
用於推薦系統判斷某個食物或料理是否符合高風險或推薦條件。
常見欄位可以包含：
basis
level
operator
amount
unit
condition
note

basis 可使用：
per_100g
per_serving
per_day
food_category
fat_quality
glycemic_impact
disease_stage
symptom_trigger

6. example_foods
保留原始參考文件中提到的代表性食物。
注意：這只是輔助說明，不是知識圖譜主要關係。

7. reason
用一句話說明此疾病為什麼和這個營養成分有關。

九、疾病整理方向

請依照以下疾病特性整理，但所有營養成分都必須映射到 nutrition_components.json 中存在的 nutrition_id，或先依第三段規則新增為 NNUT 後再使用。

1. Hypertension 高血壓
常見營養關係：
limit NUT017 鈉
recommend NUT018 鉀
recommend NUT009 膳食纖維
limit NUT006 飽和脂肪
limit NUT104 酒精含量
diet_pattern 可包含 DASH

2. Hyperlipidemia 高血脂
常見營養關係：
recommend NUT009 膳食纖維
recommend NUT067 脂肪酸M總量
recommend NUT073 脂肪酸P總量
recommend NUT078 廿碳五烯酸(20:5)
recommend NUT080 廿二碳六烯酸(22:6)
limit NUT006 飽和脂肪
prohibit NUT083 反式脂肪
limit NUT103 膽固醇
limit NUT010 糖質總量
limit NUT017 鈉

3. Diabetes Mellitus 糖尿病
常見營養關係：
limit NUT010 糖質總量
limit NUT008 總碳水化合物
recommend NUT009 膳食纖維
limit NUT017 鈉
limit NUT006 飽和脂肪
若原始資料提到低 GI 或精製碳水，請在 reason 或 note 說明，因為 nutrition_components.json 沒有 GI 或 refined carbohydrate 欄位

4. Cardiovascular Disease 心血管疾病
常見營養關係：
limit NUT017 鈉
limit NUT006 飽和脂肪
prohibit NUT083 反式脂肪
limit NUT103 膽固醇
recommend NUT009 膳食纖維
recommend NUT067 脂肪酸M總量
recommend NUT073 脂肪酸P總量
recommend NUT078 廿碳五烯酸(20:5)
recommend NUT080 廿二碳六烯酸(22:6)
limit NUT010 糖質總量

5. Chronic Kidney Disease 慢性腎臟病
常見營養關係：
limit NUT017 鈉
limit 或 adjust_by_stage NUT004 粗蛋白
limit NUT018 鉀
limit NUT023 磷
需特別標記：慢性腎臟病飲食限制會依疾病分期、是否洗腎而不同，不可用單一規則套用所有人

6. Stroke 腦中風
常見營養關係：
limit NUT017 鈉
limit NUT006 飽和脂肪
prohibit NUT083 反式脂肪
recommend NUT009 膳食纖維
recommend NUT018 鉀
recommend NUT067 脂肪酸M總量
recommend NUT073 脂肪酸P總量
limit NUT010 糖質總量
主要目標是控制血壓、血脂、血糖與心血管風險

7. Metabolic Syndrome 代謝症候群
常見營養關係：
limit NUT010 糖質總量
limit NUT008 總碳水化合物
limit NUT006 飽和脂肪
prohibit NUT083 反式脂肪
recommend NUT009 膳食纖維
recommend NUT067 脂肪酸M總量
recommend NUT073 脂肪酸P總量
limit NUT017 鈉
與腹部肥胖、血壓、血糖、三酸甘油脂、HDL 有關

8. Gout 痛風
常見營養關係：
limit 或 prohibit NUT104 酒精含量
limit NUT012 果糖
recommend NUT003 水分
limit NNUT001 普林
若原始資料提到普林、高普林食物、內臟、海鮮，因為 nutrition_components.json 原始資料沒有 Purine 欄位，且普林對痛風飲食規則很重要，請依第三段規則新增 NNUT001 普林後再建立 Disease-Nutrition 關係。
內臟、海鮮本身應放在 example_foods，不可作為 nutrition component。

9. Hyperuricemia 高尿酸血症
常見營養關係：
limit NUT104 酒精含量
limit NUT012 果糖
recommend NUT003 水分
limit NNUT001 普林
與痛風類似，但偏向預防與控制尿酸。
若原始資料提到普林，請依第三段規則新增 NNUT001 普林後再建立 Disease-Nutrition 關係。

10. Gastroesophageal Reflux Disease 胃食道逆流
常見營養關係：
limit NUT005 粗脂肪
limit NUT104 酒精含量
limit NNUT002 咖啡因
limit NNUT003 辛辣刺激成分
limit NNUT004 酸性成分
limit NNUT005 碳酸
若原始資料提到咖啡因、辛辣、酸性食物、碳酸飲料，因為 nutrition_components.json 原始資料沒有這些欄位，且這些屬於胃食道逆流重要飲食觸發因子，請依第三段規則新增對應 NNUT 後再建立 Disease-Nutrition 關係。
注意：此疾病常與症狀觸發食物有關，因此 food_level_rule 可使用 symptom_trigger。

十一、程式處理要求

請將所有程式處理都放在：

workspace/src/chronic_disease_rules

請先檢查該資料夾中現有檔案與程式碼，再依照現有架構修改。

不要把程式散落到其他資料夾。

若需要新增檔案，請放在此資料夾內，並使用清楚命名，例如：

chronic_disease_rules.json
build_chronic_disease_rules.py
validate_chronic_disease_rules.py
nutrition_rule_schema.json

如果資料夾中已經有類似檔案，請優先修改既有檔案，不要重複建立功能相同的新檔案。

若新增 NNUT 營養成分，必須同步更新 nutrition_components.json，並確保 disease_nutrition_relations 使用的 NNUT 欄位與 nutrition_components.json 完全一致。

十二、資料品質要求

1. 不要省略任何疾病
2. 不要省略任何整理出的規則
3. 不要只列食物，必須轉成營養成分或 non_nutrition_rule
4. 不要讓 disease 直接連 food
5. example_foods 可以保留，但只能作為輔助說明
6. relation 必須只能是 recommend、limit、prohibit
7. disease_nutrition_relations 中的 nutrition_id 必須存在於 nutrition_components.json
8. disease_nutrition_relations 中的 nutrition_name_zh、nutrition_name_en、nutrition_unit、nutrition_category、source_column 必須和 nutrition_components.json 完全一致
9. 不可使用 snake_case 自訂 nutrition_id
10. 若 nutrition_components.json 中不存在必要營養成分，必須先判斷是否能合理映射到既有營養成分；若不能，才依第三段規則新增 NNUT 編號
11. 同一疾病中，如果同一 nutrition_id 已存在相同 relation，不要重複建立
12. 如果不同疾病都限制 NUT017 鈉，可以重複出現在不同疾病中，這是合理的
13. 若規則有共病條件，請放進 note 或 risk_notes，不要硬套成絕對規則
14. 若參考文件只有食物描述，請推論其主要營養成分原因，但 reason 要寫清楚
15. 若該原因可映射到既有 nutrition_components.json，請建立 disease_nutrition_relations
16. 若該原因無法映射到既有 nutrition_components.json，但屬於重要營養成分、食物成分或飲食因子，請新增 NNUT 後建立 disease_nutrition_relations
17. 若該原因只是食物、料理、飲食情境或行為描述，不要新增為 nutrition component，請放進 example_foods、non_nutrition_rules 或 unmapped_concepts
18. 若無法確定某項數值，請標記為「需依資料庫校正」或 null，不要亂填過度精準的數字
19. 產出後請驗證所有 disease_nutrition_relations 的 nutrition_id 都能在 nutrition_components.json 找到
20. 產出後請驗證所有 disease_nutrition_relations 的 nutrition 欄位是否和 nutrition_components.json 完全一致
21. 產出後請驗證新增 NNUT 編號沒有重複，且從 NNUT001 依序編號
22. 產出後請驗證 JSON 可以被程式直接 parse

十三、最終輸出限制

最終回覆請遵守：

1. 只輸出 JSON
2. 不要解釋
3. 不要 markdown
4. 不要省略任何規則
5. 將所有參考文件整理成一份 JSON 資料，並輸出至 workspace/src/chronic_disease_rules/output/chronic_disease_kg_rules_20260507

9. 不要在 JSON 前後加任何文字
